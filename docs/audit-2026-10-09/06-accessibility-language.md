# Audit 06 - Accessibility, Plain Language, Resilience UX (web dashboard)

Date: 2026-10-09. Scope: `web/` (vanilla JS, no bundler). Method: static reading of `web/src`, `web/css`, `web/index.html`. Nothing was run in a browser, with a screen reader, or on a device. All citations are `web/...` paths relative to the repo root unless noted.

Severity: P0 blocks use for some users, P1 wrong or misleading, P2 friction, P3 polish.
Effort: S under half a day, M one to three days, L more than three days.

## Findings

### D. Filipino labels

Findings only; nothing translated.

- The UI is English only and hard-coded in about 40 JS files (`<html lang="en">` at `web/index.html:2`). No string table, no `i18n` helper exists (grep: none). Adding Filipino later would mean touching every file, so decide early whether it is wanted.
- English is the working language of Philippine government forms and these annexes, and the new workflows copy DILG form names (Annex B, C-1, D). Staff already use English terms such as "Incident", "Dispatch", "Roster", "Approve". The need is therefore for plain English first.
- Terms where a Filipino or local label would probably be expected: Tanod (already used), Punong Barangay (used), Kagawad (never appears in the UI; staff would look for it, see X-23), "Sangguniang Barangay" (absent), "Barangay Secretary" (UI says "Secretary"), "Blotter" (removed by design, but staff may search for it), "Lupon" (no account by design). The SMS/mobile side may need Filipino for citizens; that is out of scope here.
- Recommendation: do not build an i18n layer now. Fix the glossary (below), then ask 3 to 5 actual users (Secretary, Chief Tanod, a Kagawad, a Tanod) whether a Filipino toggle would help. `could not verify` whether any barangay official has asked for one.

Suggested glossary (to confirm with the barangays): Punong Barangay; Chief Tanod (show instead of "Admin"); Barangay Secretary (instead of "Secretary"); Kagawad (document the account type); Tanod; Incident; Responder; Duty roster.

## What is solid

- Skip link, landmarks (`aside`, `nav`, `header`, `main`), `aria-current` on the active nav item, focus moved to the page heading on every route change (`main.js:231-236`), per-route `document.title` (`main.js:207-212`).
- `ConfirmDialog.js` is a model dialog: `aria-modal`, focus trap, Escape, focus return, safe default focus, async submit with disabled buttons and an inline error.
- `Menu.js`: `aria-haspopup`, `aria-expanded`, `aria-controls`, arrow-key roving, Escape with focus restore.
- `DataTable.js`: `<caption>`, `scope="col"`, `aria-sort`, real-button row activator instead of `role=button` on `<tr>`, `aria-live` row summary and pagination status.
- Charts: SVG hidden from AT with a visually hidden data table (`LineChart.js`/`BarChart.js:135-141`); donut has `role="img"` with labels.
- Login: visually hidden labels, `aria-invalid` and `aria-describedby`, Caps Lock warning, password toggle with `aria-pressed`, disabled controls while signing in, focus returned to the password field.
- `DateRangePicker`: labelled dates, inline validation with `role="alert"`, Escape, defaults computed in Asia/Manila.
- Reduced motion handled globally (`base.css:1097-1104`); dark mode uses specific `-text` and `-solid` tokens for contrast; 16 px base text; 40 px control height.
- Failed network calls produce a specific message ("Could not reach the Baranguard server...", `apiClient.js:148`) and most data pages have a Retry state; CSV export neutralises formula injection; the statistical export confirms with a toast.
- Timestamps from the API are correctly tagged UTC (`apiClient.js:204-212`).
