# Baranguard — Full Codebase Audit, 2026-09-07

**Scope:** bugs, logic errors, and business-rule violations across
`backend/`, `web/`, and the interface to `mobile/`. **Audit only — no
code was changed by this pass.** Doc reconciliation from these findings
landed in `docs/HANDOFF.md`, `docs/REMAINING.md`, `docs/REFERENCE.md`
and `docs/SPRINTS.md`.

**Method.** Route-table enumeration; a rule-by-rule trace of §2's eleven
non-negotiables through the controllers that implement them; a
mechanical scan of every `innerHTML`/`insertAdjacentHTML` template
literal in `web/src` for unescaped interpolation; `git diff` review of
the uncommitted working tree; and a claim-by-claim check of the
auto-loaded docs against the code.

**What passed.** Route count is genuinely 77 (+6 internal), matching §5.
Rule 4 holds — `AiDraftController::approve()` is the only writer of
`incident.redacted_narrative`. Rule 5 holds — the three `new
OllamaClient()` sites in `AiDraftController` call only `isConfigured()`
and `model()`, never the network. Rule 11 holds — `ReportsController`
buckets on real Asia/Manila calendar days converted to UTC bounds, no
`CONVERT_TZ()`. Rule 8 holds — no `Audit::record()` call passes
narrative, credentials, coordinates or personal data. Cross-tenant is
404 everywhere it should be; the four `403`s are all within-tenant role
or ownership checks. `verify-web-wiring.mjs` is 497/497 and every file
under `web/src` parses clean under `node --input-type=module --check`.

## P0

### F1 — The API is currently published to the public internet

`web/index.html:142` (uncommitted working-tree change):

    window.BARANGUARD_API_BASE_URL = 'https://wheels-howto-obvious-describing.trycloudflare.com/api/v1';

§1 fixes this as an offline-first, **locally hosted, LAN-only, no-cloud**
system, and `backend/public/index.php`'s permissive CORS default is
justified in its own comment by exactly that assumption. `backend/.env`
sets no `CORS_ALLOWED_ORIGIN`, so the served value is `*`.

Three consequences, not one:

1. Every endpoint — including `POST /auth/login` — is reachable from any
   origin on the internet for as long as the tunnel is up.
2. **It breaks the citizen-report rate limit into a global bucket.**
   `CitizenReportsController::submit()` throttles on
   `$_SERVER['REMOTE_ADDR']`. Behind a tunnel every submitter presents
   the tunnel's local address, so all citizens share one counter: one
   spammer locks out the whole barangay, and a real flood is invisible.
3. It points the app at `baranguard_uiseed`, the disposable preview DB —
   not the real `baranguard`.

Committed `HEAD` is no better: it reads `http://127.0.0.1:8140/api/v1`,
also the preview DB. `docs/HANDOFF.md`'s "✅ RESOLVED 2026-09-05: web app
reverted to the real API" banner claims `8081` and is simply false —
that value has not been in the file since `f918090`.

### F2 — Stored XSS from an unauthenticated endpoint into the Secretary session

The one session in the system that can read every `raw_narrative` in the
barangay is reachable by an anonymous attacker, in four hops:

1. `POST /citizen-reports` is unauthenticated
   (`backend/routes/citizen-reports.php`, `requiresAuth = false`).
   `description` is validated for presence and a 2000-char cap and
   stored verbatim — no sanitization, no encoding.
2. A Secretary or Admin converts the report;
   `CitizenReportsController::convert()` copies `description` straight
   into `incident.raw_narrative`.
3. The Secretary opens Blotter Detail and clicks the blotter excerpt /
   print action. `web/src/pages/blotter-detail.js:135`, inside the
   `modal.innerHTML` template that starts at line 78:

       ${blotter?.narrativeSummary || incident.redactedNarrative || incident.rawNarrative || 'No official summary provided.'}

4. The session token lives in `sessionStorage`
   (`web/src/api/apiClient.js:53`), readable by the injected script.

The rest of that same file handles the narrative correctly with
`textContent` (lines 611, 624, 923, 1012) — the print modal is the one
place it does not, which is why it survived review.

`contact_number` is the same chain with a shorter fuse: capped at 32
characters, which is enough for a working payload, and rendered
unescaped at `web/src/pages/citizen-reports-inbox.js:421`. That one needs
no conversion step — it fires the moment an Admin opens the inbox.

This is a §2 Rule 1 exfiltration path: `raw_narrative` leaving the system
through something other than the approved AI pipeline.

### F3 — The same unescaped-`innerHTML` pattern is systemic

A mechanical scan of every `innerHTML` / `insertAdjacentHTML` template in
`web/src` found roughly forty further interpolations of server data with
no escaping. Only three modules define an `escapeHtml` helper
(`admin-dashboard.js:682`, `dispatch-center.js:64`,
`gis-live-tracking.js:614`) and none of the three uses it on every site.

Ranked by whose input reaches them:

| Site | Field | Written by |
|---|---|---|
| `blotter-detail.js:135` | narrative | anonymous (via F2) |
| `citizen-reports-inbox.js:421` | `contactNumber` | anonymous |
| `blotter-detail.js:472,487,517,555` | complainant/respondent/contact, location, officer | Secretary, Tanod (mobile) |
| `blotter-list.js:535` | the same five fields, per ledger row | same |
| `incident-management.js:1268` | `phoneStr` into `href="tel:${...}"`, `officerName` | same |
| `sms-monitor.js:697,1745` | `convo.phoneNumber`, `row.failureReason` | inbound SMS sender, gateway |
| `scheduler.js:272,282` | `shift.patrolZone` | Admin |
| `swap-requests.js:235,247` | requester/target name | Admin |
| `map-packages.js:300` | `pkg.version` | map-package uploader |
| `audit-log.js:580` | `actorUsername`, `entityType` | Admin |
| `settings.js:707` | `general.system_name` / `municipality` / `region` | Admin (self-XSS only) |

The bottom rows are low-severity — an Admin attacking their own session
is not a threat model. The top five are not.

## P1

### F4 — Evidence attachment upload does not exist on the server

`evidence_attachment` has **no writer anywhere in `backend/`**. There is
no `POST /incidents/:id/evidence` route (`backend/routes/incidents.php`
has only the `GET`), no `INSERT INTO evidence_attachment` in any
controller, service or script, and `SyncController::batch()` accepts only
`incidents`, `gps_tracks`, `duty_status_updates`,
`dispatch_status_updates` and `sos` — there is no evidence channel.
Mobile writes to `evidence_attachment_local`
(`mobile/src/services/db/evidenceRepository.ts:40`) and nothing ever
ships those rows anywhere.

So `GET /incidents/:id/evidence` returns an empty list forever in
production, and three shipped mechanisms govern a table that cannot be
populated: `RetentionService`'s evidence purge, `evidence_attachment.
legal_hold`, and §11's evidence retention window.

`docs/REMAINING.md` C4 records only "Evidence files can't be downloaded
from W7 (no authorized byte-serving endpoint)". That is true and much
too narrow — they cannot be uploaded either, which is a missing feature,
not a missing convenience. Photo/voice capture is listed under A1 as
"device-unverified"; it is in fact **unbuilt end-to-end** regardless of
what the device run shows.

### F5 — `PATCH /incidents/:id` idempotency is theatre

`IncidentsController::update()` (lines 587-590) requires an
`Idempotency-Key` header and rejects a non-UUID with 400 — then never
stores it, never looks it up, and never replays. §2 Rule 3 is "a retry
must return the original row, never create a second." Every sibling
write honours that for real: `createWeb()` replays on
`incident.client_event_id`, `BlotterController::createEntry()` on the
same column, `SmsController::send()` on `sms_log.correlation_id`.

Practically: a double-submit writes a second `incident_updated` row to
`audit_log` for the same edit, and the required header buys nothing. The
endpoint has never been called over HTTP (per `HANDOFF.md`), so this has
not surfaced.

### F6 — `is_suspended` is not checked on authenticated requests

`AuthMiddleware::authenticate()` selects `u.is_active` and rejects on it,
with a comment naming the check as defense-in-depth for the window
between deactivation and session revocation. Migration 0011's
`is_suspended` — described in §4 as "a third, independent axis from
is_active" — has no equivalent line.

It is currently unreachable in practice: `AuthController::login()` does
check it (line 84), and `UsersController::updateStatus()` revokes every
session in the same transaction as the suspension. The gap bites only
when suspension is set outside that endpoint — direct SQL, a restore, or
any future code path. It reads as an omission rather than a decision,
since the neighbouring axis got the belt-and-braces treatment.

### F7 — Walk-in blotter puts unredacted intake text in front of Admin and PB

`BlotterController::createEntry()` writes the Secretary's text to
`incident.raw_narrative` **and** to `blotter_record.narrative_summary`,
and creates the record already finalized (`revision_no = 1`,
`finalized_at` set). §4 notes `narrative_summary` is "shared with
Admin/PB once finalized" — so on a walk-in, text that also lives in
`raw_narrative` is Admin- and PB-readable immediately, with no redaction
step anywhere in the path.

This is defensible: the Secretary authored the summary knowingly, and it
is the same lifecycle `finalize()` has always had. But it is the only
path in the system where `raw_narrative` content is legitimately
readable by a non-Secretary, and neither §2 Rule 1 nor §5's `POST
/blotter` note says so. Either the rule needs the carve-out written
down, or the walk-in flow needs two distinct fields.

## P2

### F8 — `POST /blotter` can answer `200 []`

`POST /incidents` and `POST /blotter` share one idempotency namespace —
`(barangay_id, device_id IS NULL, client_event_id)` — but read it with
different queries. `findWalkInByKey()` JOINs `blotter_record`; the
in-transaction `FOR UPDATE` recheck (line 306) does not.

If a key already belongs to an incident with no blotter row, the
pre-check misses, the recheck hits, and control reaches:

    Http::send(200, self::findWalkInByKey($pdo, $barangayId, $idempotencyKey) ?? []);

`findWalkInByKey` returns null again, so the client gets HTTP 200 with a
body of `[]` — an empty JSON array where a ledger object is documented.
Not a data-corruption bug (the transaction rolls back correctly), but it
is an undocumented response shape on an endpoint Sprint 8's "valid JSON
contracts" box will schema-validate.

### F9 — Enter double-toggles the GIS Live Activity panel (uncommitted)

`web/src/pages/gis-live-tracking.js`, in the working-tree diff: the
collapse `<button>` gets a click handler, and its ancestor header gets
both a click handler and a `keydown` handler for Enter/Space.

Pressing Enter while the button is focused fires the button's native
click (toggle 1); the `keydown` also bubbles to the header, which calls
`preventDefault()` and toggles again (toggle 2). Net effect: nothing
happens. Space works, because the header's `preventDefault()` runs first
and suppresses the button's own activation, leaving exactly one toggle.

### F10 — `avg_response_time_minutes` double-counts multi-dispatch incidents

`ReportsController::summary()` (line 180) and the export path (line 606):

    SELECT AVG(TIMESTAMPDIFF(MINUTE, i.created_at, d.arrived_at))
    FROM incident i JOIN dispatch d ON d.incident_id = i.incident_id
    WHERE ... AND d.arrived_at IS NOT NULL

No de-duplication. An incident with two arrived dispatches (a reassign,
a second responder) contributes two samples and is weighted twice. §6
defines the metric per incident. `response_time_trend[]` (line 205)
inherits the same shape.

This is exactly the number Sprint 8's "Dispatch response-time metric"
box is meant to report as measured, so it should be settled before that
box is picked — the fix is a per-incident `MIN(d.arrived_at)`, but which
dispatch counts is a definition question, not a code question.

### F11 — Broadcast idempotency full-scans `audit_log`

`SmsController::broadcast()` finds a prior broadcast with
`JSON_UNQUOTE(JSON_EXTRACT(metadata_json, '$.idempotency_key'))` against
an unindexed column on an append-only table that only grows. Two
problems: it degrades with the audit log's lifetime, and it makes
`audit_log` load-bearing for write correctness rather than a pure
record. §4 calls that table "write-once except retention" — retention
pruning old rows would silently reopen the idempotency window.

## Suggested order

1. **F1** — one line, and it is the difference between a LAN system and
   a published one. Decide the intended base URL and whether the tunnel
   should exist at all.
2. **F2 + F3** — one shared `escapeHtml` helper applied at the ~45 sites,
   or convert the affected templates to `textContent`. The top five rows
   of F3's table are the ones that matter.
3. **F4** — a real decision, not a fix: build the upload endpoint and the
   sync channel, or write down that evidence is out of scope and stop
   claiming §11 retention covers it.
4. **F5, F6, F8** — small, contained, each an afternoon.
5. **F10** — settle the definition before Sprint 8's metric box.
6. **F7** — a documentation decision first, then possibly a schema one.
