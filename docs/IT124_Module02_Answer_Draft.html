ERD Recap and Migration Schema

SLO 2 · Applying · 10 pts
Member(s) who worked on this item: FILL

Entities chosen: incident and dispatch — the two core entities the SDD's own data dictionary (§4.3) details, joined by "An Incident may have zero or many Dispatches; a Dispatch must belong to exactly one Incident" (§4.2).

How Baranguard codes a migration. The SDD (§3.2) chose PHP 8.2 with no framework, so a migration is a plain MariaDB SQL file, applied in numbered order by backend/scripts/bootstrap-db.sh and by every verify-*.sh suite, each paired with a .down.sql. Both tables are created in backend/migrations/0001_baseline_schema.sql; incident was later altered by 0007, 0008, 0010 and 0014. The schema below is the current state after all 22 migrations. The Constraint column uses the module's four words only — required, foreign key, unique, none (none = optional / nullable); defaults and delete rules are in the last column.

Foreign keys vs. the ERD. Five of the eight foreign keys above match a drawn relationship: barangay→incident, user→incident, mobile_device→incident (Figure 2, left column), incident→dispatch and user(Tanod)→dispatch (SDD §4.2 bullets 2–3). Three — incident.redaction_approved_by, dispatch.dispatched_by, dispatch.cancelled_by, all → user — are real in the migration but not drawn in the simplified Figure 2, which shows one user→incident and one user→dispatch line. None is invented; the ERD needs three extra user lines (or a note that Figure 2 is simplified) in the SDD addendum listed under Before you print.

Migration as actually coded — excerpt of 0001_baseline_schema.sql

CREATE TABLE dispatch (
  dispatch_id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  incident_id             BIGINT UNSIGNED NOT NULL,
  dispatched_by           BIGINT UNSIGNED NOT NULL,
  tanod_id                BIGINT UNSIGNED NOT NULL,
  priority                ENUM('normal','high','critical') NOT NULL,
  route_json              JSON NULL,
  route_status            ENUM('available','unavailable','stale') NOT NULL DEFAULT 'unavailable',
  status                  ENUM('assigned','en_route','arrived','completed','cancelled') NOT NULL DEFAULT 'assigned',
  dispatched_at           DATETIME NOT NULL,
  en_route_at             DATETIME NULL,
  arrived_at              DATETIME NULL,
  completed_at            DATETIME NULL,
  cancelled_at            DATETIME NULL,
  cancelled_by            BIGINT UNSIGNED NULL,
  created_client_request_id CHAR(36) NOT NULL,
  UNIQUE KEY uq_dispatch_client_request (created_client_request_id),
  KEY idx_dispatch_incident_status (incident_id, status),
  KEY idx_dispatch_tanod_status_dispatched (tanod_id, status, dispatched_at),
  CONSTRAINT fk_dispatch_incident      FOREIGN KEY (incident_id)   REFERENCES incident(incident_id) ON DELETE RESTRICT,
  CONSTRAINT fk_dispatch_dispatched_by FOREIGN KEY (dispatched_by) REFERENCES user(user_id)         ON DELETE RESTRICT,
  CONSTRAINT fk_dispatch_tanod         FOREIGN KEY (tanod_id)      REFERENCES user(user_id)         ON DELETE RESTRICT,
  CONSTRAINT fk_dispatch_cancelled_by  FOREIGN KEY (cancelled_by)  REFERENCES user(user_id)         ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

Requirement 2

Module Inventory and MVC Build Plan

SLO 1 · Applying · 10 pts
Member(s) who worked on this item: FILL

Naming convention used — Baranguard's own, per SDD §3.2 "no framework dependency". The four artifacts the module names map to this codebase as follows; a fifth line, View, is added for orientation only and is not one of the four.

ArtifactBaranguard convention
Migrationbackend/migrations/NNNN_<snake_name>.sql + paired NNNN_<snake_name>.down.sql; plain MariaDB DDL, applied in numeric order, never edited once applied (a fix is a new number).
Model (data access)There is deliberately no ORM. backend/models/ documents the rule; the Model role is filled by parameterized PDO prepared statements ($pdo->prepare(...)->execute([...]), never string-concatenated SQL) inside the owning controller, plus a backend/services/<area>/<Name>.php class wherever business rules outlive one request.
Controllerbackend/controllers/<Name>Controller.php — a final class of static handlers (PDO $pdo, array $identity, ...$routeParams); role / tenant / ownership checks happen here via AuthMiddleware::requireRole() and requireTenant().
Routebackend/routes/<resource>.php — returns a table of [METHOD, '#^/path/(\d+)$#', [Controller::class, 'method'], requiresAuth]; backend/public/index.php loads every file in that folder and matches /api/v1/*.
View (extra)web/src/pages/<screen>.js (vanilla JS dashboard, no build step) and mobile/src/pages/<screen>.tsx (Ionic React, Capacitor).

Scope of the list. These are all 20 modules the Module 01 SDD plans — every ERD box in Figure 2 and every process in the Level-1 DFD (Figure 4) is covered by one of them. All 20 have code in the repository today; the SDD plans no module that is still unbuilt (its one unbuilt item, the cloud-hosted deployment in §3.3, is infrastructure, not a module). Whether each one is done by the three-part test is a separate question answered in Requirements 8–9.

Requirement 4

Database Integration Round-Trip Evidence — Dispatch

SLO 2 · Applying · 10 pts
Member(s) who worked on this item: FILL

The round trip in our own words, naming the four layers in order:

  1. Presentation layer. The Admin opens W3 Dispatch Center (web/src/pages/dispatch-center.js), clicks Assign on a pending incident, picks an on-duty Tanod in the picker (web/src/components/DispatchAction.js, ordered nearest-first from real GPS fixes) and confirms. apiClient.createDispatch() sends POST /api/v1/dispatch with body {incident_id, tanod_id, request_id} (a fresh UUID) and the JWT.
  2. Application layer. backend/public/index.php matches the request against routes/dispatch.php; AuthMiddleware verifies the JWT and the auth_session row; DispatchController::create() checks role (Admin only), tenant (the incident must be in the Admin's barangay — otherwise 404), that the Tanod is on duty, that the same Tanod isn't already active on this incident, and that request_id hasn't been seen (a retry returns the original dispatch, never a second one).
  3. Data-access layer. Inside one transaction the controller runs prepared statements: INSERT INTO dispatch …, UPDATE incident SET status='dispatched', NotificationService::create() (a notification + notification_target for the assigned Tanod) and Audit::record('dispatch_created', …) with identifiers only.
  4. Database layer. MariaDB commits the new dispatch row, the incident.status change, the notification / notification_target / notification_delivery rows and the audit_log row atomically; FK constraints guarantee the row points at a real incident and real users.
  5. Back to the presentation layer. The API answers 201 {dispatch_id, status:"assigned", incident_id, route_status:"unavailable"}; the queue re-fetches GET /dispatch and the incident's card moves to the Active column with the Tanod's name; the Tanod's phone receives the FCM push and shows the NEW DISPATCH sheet (M12), and M5 Assignments lists the same dispatch_id.

Measured on 2026-09-19 (DEVLOG entry (4)): POST /dispatch → dispatch_id 71 → notification_delivery 26 fcm/sent at 22:08:31Z → heads-up + in-app sheet on the Infinix X6840 within ~1 s → ACKNOWLEDGE wrote notification_target.acknowledged_at 22:09:13Z.

A realistic conflict specific to this repository. Two files are touched by almost every change and are structurally prone to conflict: backend/DEVLOG.md (append-only — every session adds an entry at the end) and the numbered migration chain (backend/migrations/NNNN_*.sql, currently 0001–0022, with docs/REFERENCE.md §4 stating the range). Scenario: teammate A on feature/sos-device-fixes and teammate B on feature/sms-envelope-ingest each add a migration. Both name it 0023_…sql, both change REFERENCE.md's "Migrations 0001–0022" line to "0001–0023", and both append a DEVLOG entry. A's PR merges into develop first. When B updates their branch, Git reports conflicts in docs/REFERENCE.md and backend/DEVLOG.md — and, worse, because Git does not flag it, two different 0023_*.sql files now coexist, which bootstrap-db.sh (it globs [0-9][0-9][0-9][0-9]_*.sql) would apply in alphabetical order, silently violating the migration-order contract.

Steps to resolve it responsibly, in order

  1. git checkout feature/sms-envelope-ingest && git fetch origin && git merge origin/develop — Git stops with CONFLICT (content) on docs/REFERENCE.md and backend/DEVLOG.md; git status lists them under "Unmerged paths".
